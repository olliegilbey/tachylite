# Tachylite: design

Tachylite serves a folder of Obsidian-style Markdown as a fast, offline-capable website. It is a read-only viewer. A phone on a bad connection is the main client.

The name: tachylite is a volcanic glass, a cousin of obsidian. It comes from the Greek *tachys*, "swift". It ends in "lite".

## Why

A typical user keeps a vault of a few thousand Markdown notes, and AI agents write most of them. The user reads the vault in a browser, on a laptop and on a phone, and rarely opens Obsidian. Obsidian is slow to navigate at that size: finding the latest daily note or meeting note takes too many steps. The user also wants richer notes, with maps, diagrams and static mockups inside them.

The vault format stays exactly as it is: Markdown, YAML frontmatter, `[[wikilinks]]`. Agents know this format from training data and need nothing new. Tachylite changes how the vault is read, not how it is written.

The main client is Chrome on an Android phone, with the site installed as a PWA. Desktop browsers come second. iOS is not a v1 target.

Success: the user opens a note on a phone with no signal, and it loads at once. An agent saves a note on the server, and the open page on the phone updates in about 100 ms.

## Goals

1. Render any Obsidian-style vault to HTML, close to how Obsidian shows it.
2. Make speed the first feature, and hold it with tests (see Performance budgets).
3. Work offline after the first sync: every note and full search, on the device.
4. Push live updates to open pages.
5. Show rich content: raw HTML in notes, and standalone `.html` files as embedded pages.
6. Make navigation fast: today's daily note, recent notes by folder, a quick switcher.
7. Run light. One small Rust binary, no runtime dependencies, comfortable on a Raspberry Pi Zero 2.

## Non-goals for v1

- Editing in the browser, including ticking a task. Every write needs conflict handling with edits synced from other machines, and a write path the tailnet can reach. It is a later version.
- Authentication or multiple users. The network boundary (Tailscale) is the access control.
- Graph view, canvas, themes, plugins.
- Public internet hosting.

## Anti-goals

These make Tachylite a failure even if it works:

- Tachylite writes to the vault. It reads the vault only. All output goes to a directory outside the vault.
- An excluded note reaches the output in any form: page, search index, backlink, manifest or metadata file. (Perlite, an existing PHP viewer, leaks the full vault structure through a `metadata.json`. Exclusion applies before anything is written.)
- A client JavaScript framework or a Node build step.
- A page needs the network after the first sync.
- The project grows into a general static-site framework.

## Approaches considered

1. **Static builder with live push (chosen).** A Rust binary renders the vault to static files, re-renders only what changes, and pushes updates to open pages over Server-Sent Events. Least to break, lowest resource use, files remain valid if the process stops.
2. **Live server that renders on request.** Always fresh, no output directory. It holds more work per request, and offline caching still needs the same manifest. More moving parts for no visible gain.
3. **Off the shelf: Quartz (Node) or Perlite (PHP).** Quartz rebuilds the whole site with Node on every change. Agents write all day, so it rebuilds all day. Perlite needs PHP and leaks metadata. Neither gives control over offline sync or latency.

Docusaurus was rejected early. It compiles notes as MDX, where a stray `<` or `{` in a hand-written note fails the build. It ships a React bundle and has no wikilinks.

Existing Rust prior art: `Mathijssch/oxidian` renders Obsidian Markdown to HTML. It has no licence, so Tachylite does not reuse its code.

## Decided

### Architecture

One binary, `tachylite`. It runs as a long-lived process:

1. Full build on start.
2. Watch the vault with inotify, through `rustix`: one watch per published folder, and one on `.obsidian` for its daily-notes settings. A new folder gets its watches, then a scan.
3. On change: read every queued event in one go and apply that batch once. No debounce: an interval would spend the push budget. A save is `CLOSE_WRITE` or `MOVED_TO`, never `MODIFY`, so an edit is read once, after it is saved. The root's watch takes `MODIFY` too, for the config alone. `ATTRIB` re-reads the path, so a permission change or a time copied by `cp -p` is seen. A folder is rescanned only when it becomes readable or unreadable, since `rsync -t` sets every folder's times. A path the site would not publish is ignored. A path's last create, delete, move or save in the batch decides its state. After `CREATE`, the path is held as mid-save: a regular file there with one link keeps the published page, in this batch and in any later one that re-renders it, until its save arrives. A file found by the scan of a new folder is held the same way, since its `CREATE` came before the folder's watch. A save by `link()` sends no `CLOSE_WRITE`, and nor does a file closed before its folder's watch existed, so a hold ends after one second and the path is read as saved. Only while a path is held does the watcher wait with a timeout; otherwise it blocks, so idle costs nothing. After `DELETE` or `MOVED_FROM`, a file found at the path is mid-save for that batch, and that read holds the path. Its `CREATE` is often still queued. A file saved before its folder's watch, in a folder made again or moved into place, sends no event, so the hold's end reads it. A symlink, FIFO or hard link gets no `CLOSE_WRITE`, so it is read at once. The checks run on the file the watcher would read. So no page is published from half of a new file within its hold. A note rewritten in place, as `tool > note.md` does, is read at its `CLOSE_WRITE` but may be read half written if another note's change re-renders it first. Its close renders it and its dependents again, so the half note lasts until then. Closing that gap would take `MODIFY` on every folder, an extra wakeup on every save, so it stays. The batch copies its html pages and assets first, then renders, writes and pushes the changed notes, new notes first, so a save's own push waits for no other page. It then re-renders, in batches, the pages whose body depends on them: notes whose links now resolve differently, and embedders. Pages are written in groups of 32, each group's writes before its pushes, so a pushed page links to no page of its group not yet written. A larger apply, such as a pull that adds many notes linking to each other, can still push a page a few ms before a page it links to is written. Last, each page whose backlinks or daily neighbours changed takes its new footer and daily line around the body it already has, unrendered: the body the batch holds, or the one in its written page. A dependent that adds a backlink to a changed note pushes that note again; a page whose HTML did not change is not pushed again. An apply holds about 32 MB of rendered bodies, plus one render batch of 256 notes. The budget vault's bodies come to 27 MB, so its cold build writes each page once: a lower limit of 12 MB saved 11 MB of peak memory and cost the cold build a fifth more time, in pages written twice. A full sync past that writes its oldest pages early, and they take their final footer from the written page, so a vault of any size builds in bounded memory. On a running server, such a page is pushed twice in that sync. Index pages and the manifest follow once a non-blocking read finds the queue empty, so a burst of saves derives them once. An apply that unpublishes a page derives them at once, so no index page keeps a note that is gone or excluded. A burst that never drains still derives them once a second. A derive with no apply since the last does nothing. A config reload rewatches the tree without dropping a watch still in place, so an event queued behind the reload is still read. A write to `tachylite.toml` after its save in the batch, or queued once the reload has read it or once its rescan ends, means the read may have seen half a save. The previous config then stays until that save's own close, and the events the check read are applied next. At start-up there is no previous config, so the first sync waits for that close. If the vault folder is renamed or deleted, the server stops. Watches go by path, so a rewatch first checks that the vault's path still names the open vault, and stops the server if a parent folder was renamed.
4. Push the new HTML of each changed page to subscribed clients over SSE.
5. Serve the output directory and the SSE endpoint over HTTP on `127.0.0.1`.

The binary serves the files itself, so it controls compression, `ETag` and `Cache-Control`. It gzips each text response as it sends it, up to 256 KB for a vault file; a larger one streams as stored. The service worker fetches a page once per change, so precompressing would save no CPU. Brotli is left out: it adds 1.1 MB to the binary and saves about 120 B on a typical page. Every file response is `no-cache` with an `ETag`, so a revalidation is a 304. A page's tag hashes its content. A vault file's tag comes from its size and mtime, which the copy keeps from its source, so the tag holds across restarts and its 304 reads no bytes, and its body streams in chunks off the thread that sends pushes. There is no `Range` support. Tailscale proxies one local port.

`tachylite build <vault> <out>` runs a single build and exits, for tests and CI.

`build` and `serve` take an exclusive lock on the output directory, so two processes never write one output. `serve` reads the config, binds its port and takes the lock before it touches the output, so a bad config, a taken port or a busy output leaves the output as it was. If the output's marker vanishes under a running server, the server stops rather than write a new output.

**Live protocol.** Each note page carries `<meta name="tachylite-version">`, a hash of the page, and a script that opens `/.tachylite/events?page=<pathname>&v=<version>`. The server sends `event: page` with `id: <version>` and the full new HTML, or `event: gone` with `id: gone` when the page is removed. On connect and on every reconnect, the server compares the client's version with the current one and sends the current page if they differ. On a reconnect the browser's `Last-Event-ID` gives the client's version and overrides `v`. After `gone` that is `gone`, which matches no version, so a note back unchanged is sent again. So a phone that slept catches up, and the server keeps no history. A network error reconnects on its own. An HTTP error, as a proxy sends while the server is down, closes an `EventSource` for good, so the client opens a new stream, after 3 s and then twice as long each time, up to a minute. A hidden browser tab closes its stream and opens a new one when it is visible again, since a browser allows six HTTP/1.1 connections per origin. The client swaps `<main>`, the title and the version, and posts the page to the service worker, which stores it. On `gone` it keeps listening, and after a second it shows a notice in `<main>`. Vim and `git checkout` save by removing the note and then writing it again. Their `page` event follows within milliseconds and cancels the notice, so the page neither flashes nor reloads.

### Rendering

- CommonMark plus GFM: tables, task lists, strikethrough, footnotes, autolinks.
- `comrak` is the Markdown crate. It has a wikilinks extension.
- YAML frontmatter shown as a properties block, every key in file order. `title` names the page and its backlink entries. `tags` render as tag links. A value that is exactly one `[[link]]` renders as a link and counts as a backlink, as in Obsidian.
  Tachylite reads the YAML subset that Obsidian's Properties support: scalars, flow and block lists, and `|` or `>` block scalars. Any other value, such as a nested map, shows as its raw text. A full YAML crate would be the largest dependency in the binary, for values Obsidian itself does not edit. Frontmatter is the block between a first line of `---` and the next line of `---`.
- Wikilinks: `[[note]]`, `[[note|label]]`, `[[note#heading]]`. Obsidian's "new link format" setting writes three link forms, and a vault often mixes them. All must resolve: relative to the linking note (`[[../people/jane-doe]]`), from the vault root (`[[people/jane-doe]]`), and bare basename (`[[jane-doe]]`). Resolution order:
  1. A path starting `./` or `../` resolves relative to the linking note.
  2. A path with a `/` resolves from the vault root. When nothing is there, it resolves from the linking note's folder: Obsidian's "Relative path to file" setting writes a path down from the note without `./` (`[[sub/detail]]`).
  3. A bare name matches by basename. When several files share it (`README` in many folders), the nearest one wins: same folder, then the fewest folder steps away. A tie is a broken link.
  4. Then aliases, for a bare name only. The nearest note with the alias wins, and a tie is a broken link.
  Matching ignores case, and a note's `.md` is optional. Any other file needs its extension: `[[route.html]]`, `[[dot.png]]`. A link whose last segment names a folder (`[[people/..]]`) is missing.
  A Markdown link with no URL scheme, such as `[Jane](people/Jane%20Doe.md)`, is percent-decoded and resolved the same way. A link with a scheme, or one that starts with `/`, stays as written. A link that starts with `#`, such as `[x](#Some%20Heading)`, is percent-decoded and links to that heading in the same note, as `[[#Some Heading]]` does.
  `[[note#Heading]]` links to the heading's id, a GitHub-style slug. Tachylite writes the ids itself, without comrak's anchor link per heading.
  An unresolved link renders as `<a class="broken-link">label</a>`, with no `href`. The build logs every broken and ambiguous link: `broken link in <note>: <target>`, or `ambiguous link in <note>: <target> matches <n> files`. A running server logs a link when it newly breaks, so a re-render or a root sync logs none twice.
  An excluded note does not exist to the resolver. A link to it renders and logs exactly like a link to a missing note, so the output never reveals that it exists.
- URLs keep the vault path. A note drops `.md` and keeps its case, and the path is percent-encoded: `people/Jane Doe.md` is served at `/people/Jane%20Doe`. An `.html` page keeps its extension. There are no slugs. Two notes whose paths differ only in the case of `.md` (`a.md`, `a.MD`) would share a URL: the first in byte order wins, and the build logs the other. A note whose page name would pass the filesystem's 255-byte limit is skipped and logged the same way, so a long name never stops a build. A page or file whose name or path the output's filesystem still refuses, as one with a shorter name limit does, or a path past 4,096 bytes, is skipped and logged when its write fails. The manifest and other pages may still list it, and it returns 404. The output directory must tell names apart byte for byte, as Linux does. On a filesystem that folds case or Unicode forms, as macOS does by default, two names that fold together share one file and the last write wins: two tags in a composed and a decomposed `é`, or `a.md` beside `A.md`. Telling them apart would need Unicode normalisation tables, so that case is out of scope.
- Everything Tachylite generates lives under one reserved prefix, `/.tachylite/`: index pages, the SSE endpoint, the manifest, the service worker and client assets. Dot names are always excluded, so no vault path starts with `.`. No vault file can collide with a generated page. A vault may hold `tasks.md`, `Today.md`, or a folder note `people.md` beside `people/`. Each keeps its plain URL. The prefix mirrors `.obsidian`: a dot folder belongs to the app.
- Embeds: `![[image.png]]` shows an image, with the label as its alt text unless the label is an Obsidian size. `![[page.html]]` embeds a sandboxed iframe, with a link under it that opens the page full screen. `![[note]]` transcludes the note's body, without its properties, under a link to it. A heading embed (`![[note#Heading]]`), a pdf and any other file render as a plain link. So does a note or page embed inside emphasis, a heading or a callout title, which can hold no block.
  Transclusion nests 3 levels deep, and a note transcludes once per page. A deeper embed, or a second embed of a note already on the page, renders as a link, so a cycle ends and three small notes cannot multiply into a huge page. An embed is a link: it resolves the same way, adds a backlink, and a missing or excluded target renders and logs as broken. The links inside an embedded note stay that note's own. Its ids, and its links to them, get an `e<n>.` prefix, where `n` counts the embeds on the page. A heading slug holds no `.`, so an embed's heading and footnote ids never collide with the host's.
  When a note changes, every note that embeds it, at any depth, re-renders with it.
  A Markdown image with no scheme, `![alt](dot.png)`, resolves like a link.
- Links to HTML: `[[page.html]]` and `[label](page.html)` open the page full screen, scripts running. The page runs exactly as written, with no Tachylite shell around it. The browser's back button returns to the note.
- Obsidian callouts (`> [!note]`) and `==highlight==`.
- `%%comments%%` are stripped and never published. Obsidian does not specify every case, so Tachylite fails closed. Before parsing, it removes each comment from the note's text in note order: from a `%%` to the next `%%`, or to the end of the note. Fenced code, indented code and code spans keep their `%%`, unless a comment holds them. A backslash does not escape a `%%`. So a link inside a comment makes no backlink. A comment that runs to the end of the note hides the rest, and a notice says so. If the parser still finds `%%` anywhere outside code afterwards, in text, raw HTML, a link's URL or title, the stripper and the parser disagree about code. The note's text is then withheld, and a notice shows in its place. The note's text is also withheld when the parser reads a `%%` where the stripper opened a comment as code. Then the stripper took code for text, and its `%%` pairs may have shifted.
- No math rendering in v1; LaTeX is a later version. `$` is a literal character: notes are full of prices and shell snippets.
- Dataview, block references and image sizing are out of scope for v1.
- Tags: `#tag` in the body and frontmatter `tags`. A body tag starts a text run or follows whitespace. A tag holds letters, digits, `_`, `-` and `/`, with at least one letter or digit, at least one non-digit and no empty level, as in Obsidian. A `#` written as a character reference, such as `&#35;`, starts no tag. Anything else renders as text, and so does a tag too long for its page's file name. Each tag gets an index page at `/.tachylite/tags/<tag>`, keyed by the lowercased tag, as Obsidian matches tags in any case. The page lists the notes with the tag or a tag nested under it, as Obsidian's tag search does: `#a` lists the notes tagged `#a/b`. A tag holds no `.`, so its page `<tag>.html` never clashes with a nested tag's folder. A note's tags are its own, not its embeds'.
- Mermaid blocks render on the client. The Mermaid script loads only on pages that contain a Mermaid block. It is Mermaid's official tiny build, embedded gzipped: about 760 KB, against 1.6 MB for the full build. It has every diagram type except mindmap and architecture, and no KaTeX.
- Backlinks list at the foot of each note, in `<section class="backlinks">`, one entry per linking note, sorted by path. A note's links to itself do not count. When a link changes, the pages that depend on it change in the same batch: the linker and any note whose link now resolves differently re-render, and the old and new targets take a new footer.

### Rich content and security

Notes are trusted content, but agents write them, and a prompt-injected agent could plant a script. A script running on the main origin could read every cached note. So:

- Inline HTML in Markdown passes through Tachylite's allowlist sanitizer. It keeps layout and formatting tags and drops `script`, `iframe`, `object`, `embed`, `style` attributes, event-handler attributes and `javascript:` URLs. A link or image URL survives only with a web or mail scheme, as a path, or as a relative URL with no scheme and no character reference.
  The sanitizer rebuilds each raw HTML fragment from the allowlist: it emits only tags it builds itself, and escapes every other `<` and `>`. A tag it misreads is dropped, never run. A crate such as `ammonia` was measured and declined: it added 1.24 MB to the binary, an MPL-2.0 dependency, and 0.47 ms per note.
- Anything that needs JavaScript (a map, an interactive mockup) is a standalone `.html` file. It renders inside `<iframe sandbox="allow-scripts">`, with no `allow-same-origin`. It cannot read the main origin's storage or cache.
- Every vault file but a pdf, `.html` and `.svg` included, is served with the header `Content-Security-Policy: sandbox allow-scripts`. Opened directly as a full page, it runs in an opaque origin, so an `.svg` with a `<script>` cannot reach the main origin. A pdf keeps the main policy, since the browser's viewer needs it. Every response sends `X-Content-Type-Options: nosniff`, so no vault file loads as a script, and `Referrer-Policy: no-referrer`, so a remote image does not learn the site's address. One router-wide layer adds them, so no handler can skip them.
- Embedded `.html` pages may load from the network, for example map tiles or a library from a CDN. An embed is network-only: a sandboxed frame has an opaque origin, so the service worker never sees its request. A `srcdoc` or `blob:` frame would inherit the main policy, which blocks the page's inline script. The same page opened full screen works offline: a sync caches it, and a page over 1 MB is cached on first open. Its external assets work offline only if the browser happens to have them cached. A map can show blank tiles with no signal; that is accepted.
- Markdown links and images with a script URL (`javascript:`, `vbscript:`, `file:`, `data:` but images) lose it, as comrak's own filter would.
- The main origin sends a Content-Security-Policy that blocks inline script and every outbound request but images: `default-src 'self'; img-src 'self' data: https:; style-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'none'; form-action 'none'`. Mermaid injects `<style>`, so styles may be inline. Remote images in notes keep working.

### Navigation

- Every page shares one shell: a header, then `<main>`. The header holds the tab bar, a Find button, then the pins. The tabs are Home, Today when there is a Today page, and Recent. Each is a plain link to its tab page: `/`, `/.tachylite/today` and `/.tachylite/recent`. The bar sits at the top of the page. A tab page marks its own tab with `aria-current="page"`, which the server writes, so the mark shows with no script. Every other page marks none. The mark is a bar and a colour with no bold, so a tab keeps its width on every page. So there are four headers: the plain one, and one for each tab page. All four come from config alone, so a save, a retitle or a new day never changes any of them. A config change re-renders every page, and an open page swaps in the new header with its pushed body. An upgrade that changes the header changes every page's version, so every client syncs every page once.
- A swipe moves between tab pages. On a tab page, one finger moved sideways and lifted opens the tab beside the current one, in the header's order: a swipe to the left opens the tab to the right. It fires on release, with no finger tracking, no animation and no wrap at the ends. The move covers at least 60 px sideways, and at least twice as far sideways as up or down. Some touches are never a swipe: one that starts within 32 px of a screen edge, where a swipe is the system's Back; one that starts in an element that scrolls sideways, such as the pins row or a wide code block or table; one with a second finger; one on a page pinched in, where the move pans the page; one that selected text; and any touch while the quick switcher is open. A note page has no swipe: it has no adjacent tab. A mouse drag does nothing. The tabs stay plain links, the way in without a gesture.
  The client listens to touch events and takes nothing from the browser, which still scrolls and zooms. `touch-action: pan-y` with pointer events was built first and dropped. Under it Chromium left every code block, table and diagram its own touches whether or not it overflowed, so a swipe that started on a narrow one did nothing, and a page pinched in could not pan sideways.
- A switch from one tab page to another replaces the history entry, by tap or by swipe. So Back never walks through tabs: it returns to the page opened before them, or leaves the app. A tab opened from any other page is an ordinary link, and adds an entry.
- A switch between tab pages happens in place, with no navigation. The client puts the new tab's `<main>` in place of the one on screen, replaces the history entry, scrolls to the top, and sets the title, the header mark and the version. It closes the event stream and opens one for the page now shown, so a push for the tab just left cannot arrive late. The stream opens with the version of the copy shown, so the server sends the page at once if that copy is stale. A reload shows the tab the URL names, as the server renders it.
  The client holds a parsed copy of every other tab, and of the note Today would show, so a switch waits for no read and no parse, by swipe or by a tap across the bar. It reads them from the worker's cache itself, which needs no worker awake, and from the network on a miss. It reads them at load, after each switch, and when the worker says a sync has stored a page, so a copy is as new as the cache after each sync. A page restored from the back/forward cache keeps the copies it held until the next sync that stores a page. It picks Today's note at the switch, not when it reads the copies, so a copy held past midnight cannot show the wrong day. A switch with no copy held reads the page then. A switch that cannot read it falls back to a navigation that replaces the entry.
  This way won a measured comparison of four, logged in `docs/plans/2026-11-16-tabs.md`. The clock ran from the release of the swipe to the paint of the new tab, on the budget vault at 4x CPU throttling. A plain navigation took 57-81 ms. A swap in place with the page fetched on the switch took 22-44 ms. With the copies held ahead it takes 20-33 ms. Chrome's prerender could not be measured: Chromium never activates a prerender under DevTools control, and the bench needs that control. Holding the copies costs about 0.3 KB of client code, gzipped, and nothing measurable on a page load.
- `title` names the home page: its `<title>`, and its heading. The Home tab names the page on screen, so that heading is for screen readers only, and the list starts near the top of a phone screen. The Recent page's heading is hidden the same way. A note page opens with breadcrumbs to its folders' index pages.
- `/` is the home page: the 5 most recent notes and html pages, then the vault root's folders, notes and html pages. The 5 leave out the three newest daily notes, by the dates in their names: an agent saves today's daily note all day, and Today is one tab away. With no daily settings, they are the 5 most recent of all. The page has no link to the Recent page, since Recent is a tab.
- `/.tachylite/folders/<folder>` mirrors one folder: its subfolders, then its notes and html pages. An html page's row is its file name, `.html` included. Titles and folder names that start with an ISO date (`YYYY-MM-DD`) come first, newest first, as daily notes and meeting notes are read newest first. The rest follow by title, ignoring case.
- `/.tachylite/recent` opens with a Daily block: the three newest daily notes by the dates in their names, newest first. A Recent block follows: the 50 most recent other notes and html pages by modified time. An html page's row is titled with its file name, without `.html`, and dated by its file's modified time. An older daily note sits in the Recent block like any note. A vault with no daily settings, or no daily note, has no Daily block. Each row shows the folder and the modified date (UTC). Equal times sort by path. `/.tachylite/recent/<folder>` lists the 50 most recent notes and html pages under one folder, subfolders included, in the same form. Every folder with a note or an html page under it has one, linked from its folder index. On the budget vault that is 51 pages, and the cold build's user CPU time did not change measurably, so no cheaper rule was needed.
- Index pages are derived, not tracked. Each derive rebuilds each index page from the site's state, and writes and pushes only those whose version changed. That is O(notes), about 4 ms for 2,000 notes on the reference host. It runs after the changed notes and their dependents are pushed, once the watcher's queue is empty, and a full build runs it once after its one apply. It needs no dependency tracking, so a full build and an incremental one cannot disagree. Tag pages are the exception: a vault can hold thousands of tags, so an apply rebuilds only the pages of the tags a note gained, lost or retitled, and the tags above them.
- The quick switcher opens on Ctrl-K, Cmd-K, `/` outside a text field, or the Find button. It reads `/.tachylite/notes.json`, one `[title, url, path, alias…]` entry per note and html page. An html page's title is its file name without `.html`; its path keeps the `.html`, so a row shows which kind it opens. That file is in the manifest, so the switcher works offline. A query matches a name as a subsequence of a title, an alias or the path. A match that holds the query whole ranks before one that holds only its letters in order. Within each kind a title match ranks first, then fewer runs, then an earlier start. The same query searches every note's text: see "Search". It shows 20 rows, and Enter opens the first.
- `/.tachylite/today` is the Today tab. It shows the newest daily note dated on or before today, in place: the URL stays the tab's, so Today is a tab page. The server does not redirect: offline there is no server, a cached redirect goes stale at midnight, and the server's day is not the reader's. The page is an index page in the manifest instead. It lists the 60 newest daily notes, newest first, each link carrying its ISO date in `data-date`. The client picks the first link dated on or before the device's local date, gets that note's page, and puts its `<main>` in place of the list. A note page marks no tab, so the client keeps the Today mark in the header. The event stream follows the note, and a pushed copy is stored under the note's URL, so the cached list is never overwritten. The page's title is the note's. A relative URL in the note's raw HTML resolves against the tab's URL here, not the note's.
  The list never paints before the note. It sits in an element marked `data-pick`, which the stylesheet hides while a script can run, through `@media (scripting: enabled)`. A note's raw HTML cannot carry that attribute, so no note hides its own content. With no script the list shows. With no note to pick, or one that does not load, the client shows the list. A browser without that media query shows the list for a moment first. If the script fails to load, the list stays hidden.
  No timer runs anywhere: the list changes only when a daily note is created, renamed or removed. The client shows the pick from the page it holds at once. Unless that pick is dated today, the page may predate a note created since the last sync. So the client then asks for the list with `no-cache`, which the worker answers from the network first, and replaces the note if that list picks another. It picks again each time the browser tab becomes visible, so the tab moves to a new day's note. Between picks the tab follows the note it shows, not the list. So a daily note created while the tab is on screen shows at the next pick, and one deleted there shows the deleted notice until the list in the cache drops it. The 60 count future-dated notes too, so a vault with more than 60 notes dated ahead shows the list.
  The daily folder and date format come from `.obsidian/daily-notes.json` when present; the config's `daily` overrides them. A save of either takes effect at once. The format is Obsidian's Moment.js string, read for `YYYY`, `MM` and `DD`, with literal separators and `/` for subfolders. Any other token means no Today page, and one logged line saying why. So does an excluded daily folder. With no daily settings there is no Today page and no Today tab.
- A daily note page carries one small line under its breadcrumbs: a link to the previous daily note, and a link to the next one when there is one. Each link's text is the neighbour's ISO date. Previous and next go by the dates in the names of the published daily notes, so an excluded note is never a neighbour, and a gap in the dates is skipped. The site keeps the published daily notes in date order. A daily note that is created, renamed, deleted or excluded changes the line of the note before it and the note after it. Each takes its new line around the body it already has, unrendered, as a page takes a new backlink. So a new daily note renders one note, and rewrites and pushes at most two more. A change of daily settings renders every note, as any config change does.
- Pins: config lists links, shown on a second header line that scrolls sideways, so five pins never wrap. A pin renders from the config alone: its URL follows from its path by the URL rule, and its label defaults to the file or folder name. A pin label from the note's title would make every page depend on that note, so a retitle would push every page. A pin whose path is excluded is dropped and logged. One that matches no published path is logged after a full scan.

### Tasks

A vault already holds tasks, so Tachylite shows them. It adds no format of its own.

- A task is a list item that starts with a checkbox, anywhere in a note. It has one of four statuses: `- [ ]` todo, `- [/]` doing, `- [x]` or `- [X]` done, `- [-]` cancelled. Any other character between the brackets makes no task, and the line renders as written. comrak's task lists read `[ ]` and `[x]`. Tachylite reads `[/]` and `[-]` by the same rule, so both pairs make a task in the same places.
- The note a task lives in is its task list. Line order is priority.
- `#tags` on a task line filter it. A `[[link]]` on the line points to detail.
- No due dates and no plugin fields (Tasks or Dataview syntax).
- `/.tachylite/tasks` is an index page of every open task. `/.tachylite/tasks/<tag>` filters by tag. A wide screen shows a board, with todo and doing columns. A narrow screen shows the same page as a list grouped by task list. CSS picks the layout; there is no toggle. Done and cancelled tasks collapse to a count per task list.
- Tasks are read-only. On a note page each renders as a disabled checkbox, and its list item carries the status in `data-task`, for the board and a later write path to read. The sanitizer keeps neither `data-task` nor `<input>` from a note's raw HTML, so only a task carries the mark. A task changes when someone edits its note.
- The four statuses read apart by shape, not by colour alone: an empty box, a half-filled box, a ticked box, and a dash in the box before a struck, dimmed line. The stylesheet draws them, with no script, image or font. A list under a cancelled task keeps its own look.
- A public skill in the repo, `skills/tachylite-vault/SKILL.md`, tells an agent how to write tasks and notes that Tachylite renders well.

### Look and feel

Inspired by Obsidian's reading view and developer admin panels. Dark mode first, with a light theme from `prefers-color-scheme`. The dark theme is pure black for OLED screens, with warm text and cream links, as under a blue-light filter. The system font stack, and a monospace stack for code. No web fonts, no decoration, no animation beyond instant state changes. Readable on a phone first, then on a desktop browser. Style is a means: the page should be functional and fast, and need little thought.

### Search

- The quick switcher searches every note's text, offline, as the user types. Search has no page of its own.
- **What is searched.** The text a reader sees in a note's body: prose, code, the properties and the text of embedded notes. Breadcrumbs, the daily line and backlinks are not. An excluded note reaches no shard.
- **Matching.** A query's words, split at whitespace, must each be in the text, as a literal substring, case ignored. There is no stemming, no fuzzy match and no relevance score. The newest note comes first, by modified time.
- **Search shards.** The text lives on the device in shards. A shard is a plain text file with one row for each of its notes, in path order: the URL, the modified time and the text, with tabs between. The text is the page's body with tags dropped, character references decoded and each run of whitespace made one space. A note's shard is the FNV-1a hash of its path, modulo 512. The count is fixed, so a note that comes or goes moves no other note. A shard lives at `/.tachylite/search/<three hex digits>.txt`. The manifest's `pages` lists each one with a version of 8 hex digits, so the sync that brings pages brings shards.
- **What it costs.** On the budget vault the shards are 6.8 MB compressed, beside 12.2 MB of pages in a first sync. One save costs a client one shard, about 17 KB compressed, and the manifest is 5 KB larger. 512 was picked by measurement: 1,024 saves 3 KB a save, and its cold open is 40 ms slower.
- **The build.** The derive step writes the shards that changed, after the pages. It reads each note page of a changed shard back from the output and strips it, so the server never holds every note's text. A sink that cannot read back the pages of earlier applies builds no shard. Search follows a save within 5 s.
- **The scan.** Dedicated workers hold the text and scan it, off the page's thread. The switcher starts them when it first opens, after it asks for its list: one worker for each core but one, at most four. Each reads its share of the shards from Cache Storage, never from the network, and holds the rows newest first. It tests each row against every word, the longest first, and stops at 20 hits. A new document starts new workers, so a page's first search waits for the read: about 125 ms in the bench.
- **The rows.** 20 in all, in three groups. First the names that hold the query whole. Then the notes whose text holds every word, newest first, each with a snippet around the first word's match, the match marked. Last the names that hold only the query's letters in order. The last group waits for the workers' answer, so no row moves once it is drawn. The list says `aria-busy` while it waits. A note shows once.
- **Freshness on the device.** While the event stream is open, each open of the switcher asks the service worker for a sync. A sync that stored something tells the page. The workers then read the changed shards again, and an open switcher asks its query again.
- A client with no service worker, or a browser that gives a worker no cache, matches names only.
- Pagefind, an inverted index, and text built on the device from the cached pages each lost by measurement. `docs/plans/2026-11-19-search.md` holds the numbers.

### What gets published

Only these file types reach the output: `.md` (rendered), `.html` (sandboxed), images (`png`, `jpg`, `jpeg`, `gif`, `svg`, `webp`, `avif`), and `pdf`. Every other file stays out, whatever its folder: code, `.json`, `.env`, `.sql`, scripts. Exclusion globs apply on top. An `.svg` is served as an image, never inline, so its scripts cannot run on the main origin. A note over 1 MB is skipped and logged: a render peaks at about 12 times a note's size, and near 280 times for a pathological one, so a larger note could exhaust a small host. An html page over 1 MB is still published: Tachylite copies it without reading it, so it has no version and no sync downloads it.

### Offline sync

- A service worker caches the app shell, the search worker's script among it, and every page and search shard in the manifest's `pages`.
- The build writes `/.tachylite/manifest.json`, `{"pages":{…},"files":[…]}`. `pages` maps the URL of every note page, every index page, every search shard, the switcher list, and every html page of 1 MB or less to its version. An html page's version hashes its bytes: the build reads the page once, and writes the output file from that read, so a version and its file never come from two saves. `files` lists the URL of every html page and asset. An asset or a larger html page has no version, because Tachylite copies it without reading it. An html page with a version is in both lists. That is how the worker tells it from a page Tachylite rendered. A worker from before html pages were synced keeps it cached as a file, and fetches it on each sync until the new worker takes over. It follows the page writes of each apply, so a client that reads it finds pages at least that new.
- A page asks the worker to sync each time its event stream opens: on load, on a reconnect, and when a hidden browser tab is visible again. It asks again each time the quick switcher opens while the stream is open. The worker fetches the manifest and downloads the pages whose version changed, or that it holds no copy of, six at a time: the home page, the index pages and the switcher list first, and the search shards last, so a note is read before it is searched. It records each page's version as it goes and saves that record every 50 pages, so a sync cut short resumes where it stopped. It drops every cached URL that neither list names, outside the app shell. It never downloads a URL that only `files` lists. For an html page it records the listed version, and it never reads the page's content for a version or a diagram. A sync asked for during a sync runs once more after it. Each fetch gives up after 30 s, so a hung one cannot hold the worker's queue; the next sync retries it. An html page gets 120 s: it can be 1 MB, and a vault file over 256 KB is sent uncompressed. The worker fetches an html page past the browser's HTTP cache. The server's validator for a vault file is its size and modified time, and a tool that keeps both can change the bytes, so a revalidated fetch could store the old page under the new version. An engine without `AbortSignal.timeout`, such as iOS 15, fetches with no limit. A first sync is the whole set: on the budget vault, 12.2 MB of pages and 6.8 MB of search shards, compressed. The vault's html pages of 1 MB or less come with it. A sync that stores a page with a Mermaid diagram caches the Mermaid script last, with 120 s for its 760 KB. A new worker's first sync looks through the cached pages for a diagram, so a client that synced before the script was synced caches it too.
- A sync that stored a page or a shard tells every open page it controls. A tab page then reads again the copies it holds of the other tabs, and the search workers read their shards again.
- A page pushed to an open browser tab is posted to the worker, which stores it with the headers of the copy it replaces and records its version. A refresh begun before the push, or before a sync stored the page, does not store its older copy over it. So a browser tab that stays connected keeps its own page fresh offline.
- The worker serves every same-origin request stale-while-revalidate: the cached copy at once, and a fresh copy stored behind it. The switcher shows its cached list at once and, while its stream is open, the network's list after it, so a new note shows. Images, PDFs and html pages over 1 MB load on demand and stay cached once opened, until the manifest stops listing them.
- A page's version hashes its head template too, so an upgrade that changes the template re-syncs every client.
- The site is installable as a PWA. The web manifest and its two SVG icons are built into the binary. The second is maskable, so Android crops it to the launcher shape instead of drawing it on a white tile. Both draw the same five-facet gem in the dark theme's warm greys on black. The service worker script lives under `/.tachylite/`, so the server sends it with `Service-Worker-Allowed: /`, and the page registers it with `scope: '/'`. Both are needed for it to control the whole site.

### Configuration

Optional `tachylite.toml` in the vault root. Any other top-level key is an error, and so is `exclude` inside a table: a typo there would publish what it meant to hide. At start, a config that cannot be read or parsed is an error, so `build` and `serve` stop rather than publish. A save truncates the file before it writes it, so at start an empty config modified within the last second may be mid-save, with no event yet to show it. `build` and `serve` wait for its close, or for a second with no change to it, then read it. A config meant to be empty costs that second. The config is safe to save by rename: write a temporary file, then rename it over the config. A save in place can still be read half written in rare cases: by `build`, which has no watch, when the save has written part of the file; by `serve`, when a writer is idle for over a second after it truncated the file at start, two writers save at once, the inotify queue overflows, or a writer stalls longer than a whole rescan. A half-written config can publish what it excludes, so the README tells users to save by rename.

- `exclude`: globs, added to the defaults. They ignore case, as the publish list does. A pattern that matches no path on a full scan is logged. Any file or folder whose name starts with `.` is always excluded (`.git`, `.obsidian`, `.trash`, `.draft.md`); config cannot publish it, because the reserved prefix depends on it. `target/` and `node_modules/` are always excluded as well. Excluded means never published. Tachylite may still read config from an excluded folder, such as `.obsidian/daily-notes.json`.
- `daily`: `{ folder = "...", format = "..." }`, overriding Obsidian's daily-notes settings. `format` defaults to `YYYY-MM-DD`, as in Obsidian.
- `pins`: list of vault paths, each with an optional `|label`. A path the publish list names, such as `a.md` or `map.html`, is a file; any other is a folder.
- `title`: the home page's name: its `<title>` and its screen-reader heading. It defaults to Tachylite.
- `hosts`: names the server answers besides `127.0.0.1` and `localhost`, for the proxy in front. When set, any other `Host` gets 421, which defeats DNS rebinding. When absent, any `Host` is answered. It is read at start only, from the same read as the first sync's exclusions.

### Performance budgets

Budgets run against a synthetic vault of 2,000 notes and about 20 MB of text. A seeded generator builds it on demand; it is not committed. A small hand-written fixture vault is committed for snapshot tests.

| Budget | Target |
|---|---|
| File event to SSE push sent for the changed note itself | ≤ 10 ms |
| Dependent pages (backlinks, transclusions) and manifest updated and pushed | ≤ 250 ms |
| Save to screen, phone on a direct connection | ≤ 100 ms end to end. Headless Chrome measures it on localhost in CI; the reference phone, by hand |
| Tab switch, from the release of the swipe to the paint of the new tab | ≤ 50 ms with 4x CPU throttling, in headless Chrome |
| Cold full build, 2,000 notes | ≤ 1 s on a modern 16-core x86 machine |
| Typical note page, HTML + CSS + JS, compressed | ≤ 30 KB, no web fonts |
| Search, per keystroke, from the key to the paint of its rows, offline | ≤ 50 ms with 4x CPU throttling, in headless Chrome. The reference phone, by hand |
| Idle CPU | ~0 % |
| Resident memory, 2,000-note vault | ≤ 65 MB |
| Release binary | ≤ 5 MB, stripped |

CI enforces the deterministic budgets as absolute limits: page weight, binary size and memory. Timed budgets are set on the reference host. `make budget` measures them there, and each PR reports the numbers before and after. CI also runs the timed benches with a ceiling at three times each budget, to catch gross regressions on noisy runners. `make budget` and `make check` run the benches one at a time, so they do not slow each other. Each latency bench asserts its median within the budget and its 90th percentile within twice it, so a scheduler hiccup passes and a doubled tail fails. The dependents budget has four cases, each timed until the manifest lists the new version: a link edit, a note embedded by 100 notes, a note with 500 links that is created, retitled and deleted, and a burst of 20 saves. Headless Chrome measures save-to-screen in CI, on localhost with 4x CPU throttling. It is also measured by hand on the reference phone. Headless Chrome measures the tab switch the same way: the median of 12 swipes by real touch input, round the three tabs and back. Its budget comes from the client bench. On the budget vault at 4x CPU throttling, the slowest switch, into Today, has a median of 33 ms, and the fastest plain navigation takes 57 ms. 50 ms sits between the two, so the budget has room for a slower runner, and a change that falls back to a navigation breaks it. Headless Chrome measures search on the budget vault: the last key of four queries, five times each by real key events, from the key going down to the paint of the rows that answer it. Each query's median must be within the budget. Chrome's CPU throttle does not reach a worker, so the test stands in for a phone another way. The page runs at a quarter speed and sees two cores, which gives it one search worker, at full speed. One worker at full speed scans the vault in the time four workers take on cores four times slower: the pool a phone with five cores or more gets. The test logs the two parts, so the sum can be redone for another pool: the page's share, plus the scan at full speed times four, over the workers. On the reference host the page's share is 20 to 40 ms and the slowest scan is 10 ms. So four workers give about 32 ms on that query, two give 42 ms, and one gives 61 ms. A phone's small cores are slower than its large ones, and no emulation shows that: the figure on the reference phone, taken by hand, is the real one.

### Testing and QA

The binary is light. The repo is heavy on purpose: it carries every test and check that keeps the binary light. Three seams carry the tests, highest first:

- **Build seam.** A vault goes in, the output directory comes out. Snapshot tests of rendering, whole-output checks for exclusion and the publish list, page weight, the cold-build budget.
- **Live seam.** `tachylite serve` against a temp vault, over HTTP and SSE. Push latency, headers, idle CPU, memory. A property test applies random create, edit, rename and delete sequences and checks the live output equals a fresh full build.
- **Browser seam.** Playwright drives headless Chromium against a real server, emulating a mid-range phone and a desktop. Push to DOM, offline reads and sync, save-to-screen under CPU throttling, layout, the sandbox, zero CSP violations, and the page's transfer size. A failed test keeps its screenshot and trace as a CI artifact. Playwright is test tooling only and never ships.

The reference phone and a Raspberry Pi are checked by hand each release. A visual change is checked in a real browser, as AGENTS.md's "See it" describes.

Release binaries are static glibc builds for `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`, linked with `crt-static`, with no runtime dependencies. They are not musl builds: musl's allocator serialises the render threads. On the budget vault, the musl cold build took 1.9-2.1 s against 0.33 s for static glibc. Static glibc costs about 0.9 MB of binary size over musl. CI checks both builds. A Raspberry Pi is a portability aim, checked by hand once per release. It has no budgets of its own.

A render batch takes at most 8 threads. On a host with 8 cores and two threads per core, the cold build ran about as fast on 8 threads as on 16, for about 30% less CPU time and 3 MB less peak memory.

### Example deployment

The README documents this setup as the default route. It is an example, not built into the code.

- Host: a Linux devbox on Tailscale.
- `tachylite` runs as a systemd user service and binds `127.0.0.1`.
- `tailscale serve` proxies it on a tailnet-only HTTPS port. A port that carries a public Funnel route is public for every path on it, so Tachylite gets a port of its own.
- If the vault syncs to the host from another machine, edits made there add the sync delay before the file event.
- The host runs Linux 5.6 or later. Tachylite opens vault files with `openat2`, which confines every read to the vault, and exits with an error on an older kernel.
