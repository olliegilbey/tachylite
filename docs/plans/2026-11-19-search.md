# Search: full text in the quick switcher

**Spec:** `docs/superpowers/specs/2026-11-03-tachylite-design.md`, "Search", "Offline sync" and "Performance budgets".

**Issue:** #11.

**Goal:** the reader types in the quick switcher on a phone with no network, and sees the notes whose text holds the words, each with a snippet. A keystroke takes at most 50 ms at 4x CPU throttling on the budget vault.

## Decisions

The coordinator set these on the maintainer's word. A decision marked *open* waits for a measurement in the log below.

- **One search box.** The quick switcher. There is no search page.
- **Notes only.** Html pages and assets are not searched.
- **The query.** Case is ignored. The query splits at whitespace into words, and every word must be in the note's text. A word matches as a substring, so `shard` finds `shards` and `resharding`. Obsidian's search also matches each word independently and ignores case.
- **The ranking.** Newest first, by the note's modified time. Equal times sort by URL.
- **What is searchable.** The text a reader sees in the note's body: prose, code, the properties block and transcluded notes. Breadcrumbs, the daily line and backlinks are not. A `%%comment%%` never reaches it, since the render strips comments.
- **The rows.** Name matches where the query is a substring of a title, alias or path come first, as now. Full-text rows follow, each with the note's title, its folder and one snippet with the match marked. Name matches that are only a subsequence come last. A note shows once. This departs from the first brief, which put every name match first: on a large vault a short query fills the 20 rows with weak subsequence matches, and the full-text rows sit below the fold. The log counts them.
- **Offline.** Everything the client needs is in the manifest's `pages`, so the worker's sync fetches it with no new sync code. Search data syncs after the notes.
- **Freshness.** Search data follows a save within 5 s.
- **Exclusion.** An excluded note reaches no search data in any form.
- **One save costs bytes in proportion to one note.** The log states the bytes.
- **A page load pays next to nothing.** The search code and data load when the switcher first opens.
- **The budget.** 50 ms per keystroke at 4x CPU in headless Chromium on the budget vault, with a browser test built like the tab-switch one. Every existing budget holds.
- **The winner is the fastest candidate that keeps every budget and passes every path.** The losers' code is deleted, and their numbers stay in the log.
- **B wins.** The log gives each loser's number.
- **512 shards.** The lab picked 1,024 by the bytes one save costs. The built client picked 512 by the cold open. See "The shard count" and the build log.
- **The scan runs in dedicated workers**, since the main thread has no margin at 4x. See "The margin" in the log. The pool is one worker for each core but one, at most four. The build log gives the sum that sets it.

## Candidates

- **A. Pagefind.** The server runs Pagefind over the output and the client loads its chunked index.
- **B. Text shards.** The server writes each note's plain text into one of a fixed number of shard files. The client loads the shards and scans the text for each word.
- **C. An inverted index in shards.** The server writes a dictionary and postings per shard. The client looks words up.
- **D. Text built on the device.** The server writes nothing new. The client strips the tags from the note pages it has cached, and scans that text as in B.

## The design of B

This is the leading candidate. The design is written down before the code so a later reader can check the code against it.

**Server.**

- A note's text is its rendered body with the tags stripped, entities decoded and whitespace collapsed. The body is the span of the written page the site already tracks for a new footer. An inline tag joins the text on both sides. Any other tag becomes a space. No row holds a tab or a newline.
- A note's shard is a hash of its path, modulo a fixed count. A fixed count means a note added or removed never moves another note to a new shard.
- A shard is a file under `/.tachylite/search/`. It holds one row per note, in path order: the URL, the modified time, the text, with tabs between and a newline after. Its version is a hash of its content. The manifest's `pages` lists it.
- The derive rebuilds only the dirty shards, one at a time. It reads each member's page back through the sink, so the site holds no text between applies. A shard is dirty when a member's page was written, a member was touched, or a member left. A shard with no member is deleted.
- This is one code path: a full build dirties every shard.
- A sink says whether it reads back the pages of earlier applies. The derive builds shards only through one that does. The output directory does. The collected `Delta` that `Site::apply` returns does not, so it holds no shard and its manifest lists none. A shard with rows missing cannot be written.

**Client.**

- `search.js` is a dedicated worker. `live.js` starts a small pool of them when the switcher first opens: one fewer than the device's cores, at least one and at most four. The worker's cache holds the script with the app shell.
- Each worker takes the shards whose number, modulo the pool's size, is its own. It reads the list of shards from the worker's stored manifest, and each shard from Cache Storage directly. It goes to the network only for what the cache lacks.
- Each query word becomes a case-insensitive literal `RegExp`. A worker walks its notes newest first, tests the longest word first, and stops at 20 hits. The page merges the pools' answers by modified time and keeps 20.
- The scan runs off the main thread, so a keystroke is never blocked. A worker that is still scanning when newer queries arrive answers only the newest.
- The list carries `aria-busy` while a query waits for its answers. Tests and the bench await that.

**Scan speed.** Node, 15 runs each, median. Each note's text is its own string.

| Query | Time for all 18 MB |
|---|---|
| One letter | 0.1 ms |
| A common word | 2.4 ms |

A case-insensitive `RegExp` on the original text is as fast as `indexOf` on a lowercased copy. So the client keeps no lowercased copy, and a shard needs no JSON.

**The client today.** Bench, 20 samples: `switcher-query` at 4x CPU has a median of 54.8 ms and a 90th percentile of 60.7 ms. That clock runs from a closed switcher to the first row painted. Client files gzipped: 11,270 B (`live.js` 5,562, `sw.js` 3,140, `style.css` 2,568).

### Dead ends, with the reason

- **Shards by folder.** The daily folder holds 15% of the budget vault, and it is the shard of the note saved most.
- **A shard count that grows with the vault.** A note added at a boundary would move every note to a new shard.
- **Holding every note's text until the derive.** It breaks the memory budget.
- **Writing shards as the apply renders.** A full build and a save would then take two code paths.
- **A lowercased copy of the text on the client.** A case-insensitive `RegExp` is as fast, and every navigation is a new document that would pay the copy again.

### Lab, in headless Chromium

2026-11-19, commit `5f6e8b3`, Chromium 156.0.8078.4, load average about 2.5. A lab script, not committed, drove a phone-sized page against a server on the budget vault, after a full sync. It put the corpus above into Cache Storage as shards and timed reads and scans in the page, at full CPU speed and at 4x throttling. Each time is the median of 5 loads or 9 scans.

**The shard count.** A shard's bytes are gzipped at level 6. "One save" is the shard of a note picked at random, so a shard with more notes counts more often. The manifest is fetched whole on every sync that finds a change, so the bytes the shard entries add to it are part of what a save costs. "Short versions" are 8 hex digits in place of 16.

| Shards | Shards used | All shards | One save, shard | Manifest growth, 16 digits | Manifest growth, 8 digits | One save in all, 8 digits | Load at 1x | Load at 4x |
|---|---|---|---|---|---|---|---|---|
| 256 | 256 | 6.64 MB | 29.0 KB | 3.6 KB | 2.4 KB | 31.4 KB | 39 ms | 140-204 ms |
| 512 | 505 | 6.85 MB | 16.4 KB | 7.0 KB | 4.7 KB | 21.1 KB | 67 ms | 234-251 ms |
| 1,024 | 884 | 7.07 MB | 10.1 KB | 12.0 KB | 8.1 KB | 18.2 KB | 97 ms | 368-375 ms |

The manifest of the budget vault is 134.8 KB, 48.4 KB gzipped, before any shard entry. The load reads every shard from Cache Storage with one `match` each, all at once, and splits the rows. Reading them one after another took about twice as long.

- **1,024 shards with 8-digit versions cost a save the fewest bytes:** 18.2 KB, against 21.1 KB at 512 and 31.4 KB at 256.
- A finer split than 1,024 gains nothing: at 2,048 the manifest's growth passes what the smaller shard saves.
- The load is slower by 30 ms at full speed. It runs in workers, off the main thread, and name matches show before it ends.
- A fixed count is tuned for a vault of about this size. A vault of 10,000 notes puts about ten notes in a shard. A vault of 100 notes writes one small file per note.
- An 8-digit version is a 32-bit hash. Two contents of one shard collide once in four billion changes, and a collision leaves one client one shard behind until that shard next changes.

**The scan on the main thread.** One pass over every note's text with `RegExp(word, "i")`, newest first. "To 20" stops at 20 hits.

| Query | Hits | To 20, 1x | Whole vault, 1x | To 20, 4x | Whole vault, 4x |
|---|---|---|---|---|---|
| One letter | 2,000 | 0.0 ms | 0.2 ms | 0.0 ms | 0.9 ms |
| A common word | 1,511 | 0.1 ms | 4.8 ms | 0.1 ms | 20.5 ms |
| A rare word | 54 | 2.9 ms | 9.6 ms | 14.8 ms | 43.3 ms |
| Two words | 40 | 4.3 ms | 14.7 ms | 25.0 ms | 69.3 ms |
| Two rare words | 2 | 10.2 ms | 11.3 ms | 43.5 ms | 45.1 ms |
| No match | 0 | 5.3 ms | 4.5 ms | 17.4 ms | 16.9 ms |
| No match, with a common prefix | 0 | 12.8 ms | 12.2 ms | 59.7 ms | 53.8 ms |

**The margin.** A query with fewer than 20 hits scans the whole vault: 45-60 ms at 4x, before a row is drawn. The switcher today takes about 28 ms at 4x from the rows in the DOM to their paint. So the main thread has no margin under 50 ms, and the scan moves into dedicated workers.

**CPU throttling does not reach a worker.** A lab page ran one busy loop in the page and in a dedicated worker. With `Emulation.setCPUThrottlingRate` at 4 on the page, the page's loop took 749 ms against 172 ms, and the worker's took 187 ms against 161 ms. Sent to the worker's own target, the command fails: "Operation is only supported for pages, not workers". So the bench times the page's share of a keystroke at 4x, and the workers' scan at full speed. The budget test makes up for it: it sets the device's core count to two, so one worker scans the whole vault alone. One worker at full speed takes as long as four workers on cores four times slower.

**D, text built on the device.** The page read every cached note page from Cache Storage and stripped it with three `replace` calls.

| Reads at once | 1x | 4x |
|---|---|---|
| 1 | 920 ms | 3,444 ms |
| 8 | 530 ms | 1,871 ms |
| 64 | 480 ms | 1,760 ms |

The strip alone is 220 ms at 1x and 830 ms at 4x. The rest is 2,000 reads.

### The result so far

- **A lost** on the cold build, the memory, the binary size and the bytes of one save. See the table above.
- **C lost** on the bytes of one save: over 100 KB at the shard counts where it is small and fast, and no smaller than the text at 256 shards.
- **D lost** on the cold open, and on the ranking.
  - Every navigation is a new document, so the text must be kept or built again. Built again, each page's first search waits 1.8 s at 4x.
  - Kept, it needs a second cache that the page writes, a pass on each switcher open that finds the changed pages and strips them again, and a strip rule in the client that follows the page template. The first search on a device still waits 1.8 s at 4x, and so does the first after a change that re-renders every page, such as a config change or an upgrade.
  - No file on the device carries a note's modified time, so D cannot rank newest first. A new file of modified times would cost about 5 KB on every save.
  - D's gain is real: it adds no bytes to a first sync or to a save, and no work to the server. B adds 6.8 MB to a first sync of 12.2 MB, and 21 KB to a save. If those bytes ever matter more than the cold open, D with a kept text is the candidate to build.
- **B wins**, with the scan in workers.
