# Tabs: Home, Today and Recent, with a swipe between them

**Spec:** `docs/superpowers/specs/2026-11-03-tachylite-design.md`, "Navigation" and "Performance budgets".

**Goal:** the reader moves between the top-level pages with one swipe of a thumb, and each switch feels instant. The home page stops repeating the Recent page.

## Terms

- **tab**: a top-level page linked from the header: Home, Today, Recent. Tasks joins when the board is built.
- **tab bar**: the row of tabs in the header.
- **tab page**: the page a tab opens.
- **browser tab**: the browser's own tab. Never plain "tab".

## Decisions

Each one was agreed with the maintainer before any code.

- **The tab bar.** The header reads Home, Today, Recent, then the Find button, then the pins. "Home" replaces the site name as the home link. `title` still names the home page. Today shows only when the vault has daily settings, as before. A tab page marks its own tab with `aria-current="page"`, written by the server, so it shows with no script. The bar stays at the top: Material pairs a swipe with top tabs, never with a bottom bar.
- **The home page.** It lists the five most recently modified notes, then the vault root. The three newest daily notes are left out of the five: an agent touches today's daily note all day, and Today is one swipe away. The "All recent notes" link goes, since Recent is a tab.
- **The Recent page.** It opens with a "Daily" block: the three newest daily notes by the date in their names, newest first. A "Recent" block follows: the 50 most recently modified other notes. An older daily note sits in the second block like any note. A vault with no daily settings has no first block. The per-folder recent pages do not change.
- **Daily note neighbours.** A daily note page carries one small line at its top: a link to the previous daily note, and a link to the next one when there is one. Each link's text is the neighbour's ISO date. "Previous" and "next" go by the dates in the names of the published daily notes. So creating, renaming, deleting or excluding a daily note re-renders its two neighbours.
- **The Today tab.** `/.tachylite/today` stays the tab's URL. The client picks the note as it does now: the newest daily note dated on or before the device's local date. It then shows that note's `<main>` in place of the list, and the URL does not change. So Today is a tab page, and a swipe leaves it like any tab. The event stream follows the note shown, so the page stays live. The list never flashes before the note. The client shows the pick from the cached list at once, and replaces it if the network's list names a newer one. With no script, or no daily note, the list stays.
- **The swipe.** It works on tab pages only. A note has sideways-scrolling code and tables, and it has no adjacent tab.
  - It fires on release, for a mostly horizontal move of one finger.
  - The move starts away from both screen edges. On a phone with gesture navigation, an edge swipe is the system's Back.
  - A touch that starts in a sideways scroller, or turns into a scroll or a pinch, does nothing.
  - It does not wrap at the ends, track the finger, or animate.
  - A swipe to the left opens the tab to the right, as in every tabbed app.
  - The tabs stay plain links, which is the non-gesture way in (WCAG 2.5.1).
- **Back.** A switch from one tab page to another replaces the history entry, by tap or by swipe. Back never walks through tabs: it returns to the page opened before them, or leaves the app. A tab opened from any other page is an ordinary link, so Back returns to that page.
- **A wide screen.** The tabs are links. There is no swipe with a mouse and no new keyboard shortcut.
- **The switch is the fastest of four**, by measurement. The candidates:
  - **A.** A plain navigation.
  - **B.** A plain navigation with Chrome's prerender, through a `Speculation-Rules` header.
  - **C.** Swap `<main>` in place, fetched on the swipe.
  - **D.** Swap in place, with the neighbour tabs fetched and parsed ahead.

  The winner is the fastest that keeps the page-weight budget and passes every path: push, offline, Back, the Today pick. It gets a budget and a browser test. The losers' code is deleted, and their numbers stay in the log below.

## Slices

1. **The client bench.** A documented tool that times a user action in headless Chromium on the budget vault, at phone size, with and without CPU throttling. It prints the median and the 90th percentile. Any later optimisation can add a scenario to it. It is not part of `make check`: a bench explores, and a budget test gates.
2. **The tab pages.** The tab bar, the home page, the Recent page and the daily note neighbours. Server-rendered, with no new script.
3. **The swipe.** The swipe, the Back rule, the Today tab in place, the four-way measurement, the winner and its budget.

Slices 1 and 2 are independent. Slice 3 needs both.

### The comparison

Every run below is `make bench` on the reference host, 2026-11-16, Chromium 156.0.8078.4, on the budget vault with daily settings. Each candidate is its own binary, and one run interleaves them all. A cell is 30 kept samples unless it says otherwise, and no run dropped a sample for host load. A cell reads "median (p90)", in ms.

The `swipe-*` and `tap-*` scenarios time a tab switch. The clock starts in the page, at the release of the finger or at the tap. It stops at the first paint of content in the new tab's `<main>`, which the browser reports through Element Timing. So a navigation and a swap in place are timed to the same event. `recent-to-home` is a plain navigation to a tab page, to first contentful paint. It shows what a candidate costs a page load.

The candidates:

- **A.** A plain navigation, with `location.replace`.
- **B.** A plain navigation with Chrome's prerender. Not measured: see below.
- **C.** Swap `<main>` in place. The page is fetched on the switch, through the worker.
- **C2.** As C, but the client reads the worker's cache itself, and asks the worker only on a miss.
- **D.** As C2, and the client reads and parses ahead the tab on each side of the one shown, with the note Today would show: at load, and after each switch.
- **D2.** As D, with two faults mended. It holds the parsed pages, and picks Today's note at the switch, so a copy held past midnight cannot show the wrong day. The worker tells open pages when a sync has changed its cache, and they read their copies again, so a copy is never older than the cache.
- **D3.** As D2, but it reads ahead only after the next paint.

The gzipped client files of each candidate, as served. A adds about 1.4 KB to `main`: Today in place and the swipe, which every candidate shares. The shipped D2 differs from the measured one by comments and by small fixes from review, none on the path a switch takes.

### The result

**D2 won.** At 4x CPU, D and its variants are the fastest in every switch, in every run. Against A they cut a switch from 57-81 ms to 19-34 ms. Against C2 they save 5-10 ms on a switch into Today and 2-8 ms on the others. D, D2 and D3 are within 3 ms of each other, with no order among them: that is the noise between cells. D2 has less code than D3, and D does not pass every path.

- **A lost:** a navigation costs 57-81 ms at 4x CPU, about twice a swap in place.
- **B was not measured.** Chromium under DevTools control never activates a prerender. It reports `PrerenderingDisabledByDevTools` for every attempt, in the headless shell and in full Chromium, and `Page.setPrerenderingAllowed` did not lift it. The bench drives the browser through DevTools. So every B sample would time a navigation served from a prefetch, which is not what a phone does. Its code was a `Speculation-Rules` header and one small JSON file.
- **C lost to C2:** the round trip through the worker costs 1-7 ms at 4x CPU, and C2 needs no worker awake.
- **C2 lost to D2:** it reads and parses on the switch, which costs 5-10 ms into Today at 4x CPU. It is 284 B smaller.
- **D lost to D2:** it picked Today's note when it read ahead, so a copy held past midnight showed the old day. Its copies also stayed as old as the page load, so a tab could open staler than the worker's cache, and stay so offline.
- **D3 lost to D2:** waiting for the paint saved nothing measurable, on a switch or on a page load, and cost 50 B.

Reading ahead costs a page load nothing measurable: in run 4, D2 is within 0.5 ms of C2. Runs 1 and 2 showed D 4 ms behind A on `recent-to-home`. They also showed C2 2 ms behind A, and C2 has no code that runs on that load, so half of the gap is noise. Run 4, with twice the samples, shows none of it for D2.

Limits of these numbers:

- CPU throttling reaches the page only. The service worker and the browser process run at full speed, so the time to the response is optimistic for a phone. This flatters A and C, which wait on the worker, more than C2 and D.
- The bench's swipe is a pair of synthetic touch events, so the browser's own pan never runs. The browser suite swipes with real touch input.
- The bench waits for the page to be idle before each switch, so a copy read ahead is always ready. A switch made before then waits for the read, as C2 does.
- The headless shell has no back/forward cache. Full Chromium restored a page from it about 20 ms after Back, with the event stream open.
- The host was shared. A sample taken with under 30% of the CPU idle is dropped.
